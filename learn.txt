Middleware

Middleware runs before the controller.

authMiddleware.js → Checks whether the user has a valid JWT token.
uploadMiddleware.js → Handles resume PDF upload using Multer.
errorMiddleware.js → Handles errors and sends a proper response instead of crashing the server.

👉 Easy rule:

Middleware = Security / Checking / Processing before reaching the controller.

Flow
Request
   ↓
Middleware
   ↓
Controller
   ↓
Model
   ↓
MongoDB
   ↓
Response

Interview one-liner:

Model → Defines the database structure (schema & collection).
Middleware → Executes before the controller to validate, authenticate, upload files, or handle errors.

important:  
"I already logged in. Email and password were correct. Then why verify the token again?"
This is because HTTP is stateless.

What does stateless mean?

Every request is independent.

Example:

POST /login

Server verifies:

✅ Email
✅ Password

Creates token.

After that request finishes...

❌ Server does NOT remember that you are logged in.

Next request:

GET /profile

Server only sees:

GET /profile

It doesn't know:

Who sent it?
Is it you?
Is it another person?

So the frontend sends:

Authorization: Bearer eyJhbGc...

Now the middleware verifies:

"Yes, this token was created by me. This request is from the same logged-in user."

Without sending the token every time, the server has no way to identify you.
"Does every protected GET and POST route use middleware?"
Every protected route should use authentication middleware.

important 
1. Header

Header tells what type of token this is and which algorithm was used.

Example:

{
  "alg": "HS256",
  "typ": "JWT"
}

Meaning:

alg = Algorithm

typ = JWT

2. Payload

Payload contains the actual data.

Example:

{
  "id": "12345",
  "role": "student"
}

This data comes from your code.

Example:

jwt.sign(
{
   id:user._id,
   role:user.role
},
SECRET
)

So the payload becomes:

{
  "id":"12345",
  "role":"student"
}

3. Signature

This is the most important part.

Signature proves:

"This token was really created by my server and hasn't been changed."

Example

Secret:

mysecret123

Payload:

{
"id":"123"
}

JWT creates a signature using:

Header

+

Payload

+

Secret Key

Result:

a8dh92jj39jd...

That becomes the signature.

Why do we need the signature?

Imagine someone changes the payload.

Original:

{
"id":"123",
"role":"student"
}

Hacker changes it to:

{
"id":"123",
"role":"admin"
}

Now the payload changed.

But the signature was created using the original payload.

So when:

jwt.verify(token, SECRET)

runs,

Node generates a new signature from the current header + payload + secret and compares it with the signature inside the token.

They won't match.

Result:

Invalid Signature

↓

Unauthorized

So the user cannot become an admin by editing the token.


Header-la token type (JWT) and signing algorithm (HS256) information irukkum. 
Payload-la application-ku thevaiyana data, like user id, role, email store pannuvom.
Signature-na header + payload + secret key use panni generate pannuvanga. Verify pannumbodhu adhe secret use panni signature compare pannuvanga. Payload-a yaaravadhu modify panna signature match aagadhu, so token invalid-nu reject pannidum


important flow:

req.headers.authorization is NOT the JWT Header.

There are two different "headers"

1. HTTP Header ✅

This is part of the HTTP request.

When React sends a request:

GET /profile HTTP/1.1
Host: localhost:5000
Authorization: Bearer eyJhbGc...
Content-Type: application/json


2. JWT Header ✅

Inside the token itself, there is another header.

Example JWT:

xxxxx.yyyyy.zzzzz

It has:

JWT Header
.
JWT Payload
.
JWT Signature

The JWT Header is something like:

{
  "alg": "HS256",
  "typ": "JWT"
}

This is inside the token, not inside req.headers.

When you call:

jwt.verify(token, process.env.JWT_SECRET)
